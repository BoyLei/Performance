### 用户

消息队列堆积过多怎么处理

### 助手

这是游戏开发和高并发服务器中一个非常经典的问题。

> **消息队列堆积（Message Backlog）**本质上说明了一件事：
>
> **生产消息的速度 > 消费消息的速度。**

公式可以表示为：

```text
每秒收到消息：10000 条

每秒处理消息：7000 条
```

那么：

```text
每秒积压：

3000 条
```

时间一长：

```text
1 秒   3000 条

10 秒  30000 条

60 秒  180000 条
```

最终导致：

- 内存不断增长
- GC 压力增大
- 延迟越来越高
- 最后 OOM（内存耗尽）

---

# 游戏里一般怎么处理？

业内通常不会只有一种方案，而是**多种策略组合使用**。

# 方法一：限制每帧处理数量（最常见）

例如：

```csharp
const int MaxProcessPerFrame = 200;

int count = 0;

while (queue.Count > 0 && count < MaxProcessPerFrame)
{
    Handle(queue.Dequeue());
    count++;
}
```

假设：

```text
今天来了5000条消息
```

```text

```

```text

↓

```

### 助手

## 为什么会断开？

TCP 连接由四元组唯一标识：

```text
源 IP
源端口
目标 IP
目标端口
```

例如：

```text
客户端：192.168.1.100:51234
服务器：8.8.8.8:443
```

当你切换 Wi-Fi 时，例如：

```text
Wi-Fi A
↓

Wi-Fi B
```

客户端 IP 很可能变成：

```text
192.168.1.100
↓

192.168.10.25
```

由于**源 IP 已经变了**，原来的 TCP 四元组就不存在了。

服务器仍然认为连接来自：

```text
192.168.1.100:51234
```

而客户端现在已经变成：

```text
192.168.10.25:51234
```

双方无法继续通信，因此原来的 TCP 连接实际上已经失效。

---

## Unity 中会发生什么？

假设客户端一直在：

```csharp

```

切换 Wi-Fi 后，可能出现几种情况：

### 情况一：很快收到错误（最理想）

```text

```

例如：

```text

```

或者：

```text

```

程序立即知道连接断了。

### 情况二：一直没有数据

例如：

```text
↓

```

系统没有立即通知 Socket。

此时：


因为：

- 旧连接已经不能通信。
- 操作系统还没有检测到它已经失效。

---

例如：

客户端发送：


```text
↓

```

```text

```

这个过程可能持续几十秒甚至更久（取决于操作系统和 TCP 参数）。

所以很多人会觉得：

> Wi-Fi 已经切了，但 Socket 为什么还没断？

原因就在这里。

### 总结

对于**普通 TCP 连接**来说：

- **Wi-Fi 切换通常会导致连接失效。**
- **TCP 不会自动迁移到新的网络。**
- 是否立刻收到断开通知取决于操作系统和网络状况，有时会立即报错，有时需要等待超时。
- 在 Unity 或游戏开发中，通常依靠**心跳检测 + 自动重连**来快速恢复连接，而不是等待 TCP 自己判断断线。

### 用户

TCP 有没有办法知道客户端发的消息服务器有没有收到

### 助手

这是一个非常经典的问题，也是很多游戏开发者容易混淆的地方。

答案分两层：

> **TCP 可以保证数据送达对方的 TCP 协议栈，但不能保证你的服务器业务代码已经处理了这条消息。**

这两者区别非常大。

---

# 第一层：TCP 能知道数据是否到达服务器吗？

**可以。**

TCP 内部有 **ACK（Acknowledgment，确认应答）** 机制。

例如：

客户端发送：

```text
Hello
```

TCP 实际做的是：

```text
客户端
    │
    │ Hello（Seq=100）
    ▼
服务器 TCP
```

服务器 TCP 收到后，会立即回复：

```text
ACK=105
```

意思就是：

> **"我已经收到序号 100~104 的数据了。"**

客户端收到 ACK 后，就知道：

```text
数据已经成功到达服务器的 TCP 接收缓冲区。
```

如果一直收不到 ACK：

```text
Hello

↓

没有 ACK
```

TCP 会：

```text
重传

↓

重传

↓

重传
```

直到：

- 收到 ACK
- 或者超时，认为连接断开

---

# 但是，这只是到了 TCP 层！

很多人误以为：

```text
ACK

=

服务器业务已经收到
```

实际上不是。

例如：

服务器：

```text
TCP
↓

Receive Buffer
↓

你的程序
```

ACK 的发送发生在：

```text
TCP

↓

ACK
```

而不是：

```text
你的程序
```

也就是说：

服务器内核刚收到数据：

```text
Hello
```

TCP 就回复：

```text
ACK
```

但是你的程序：

```csharp
socket.Receive(...)
```

可能：

- 10ms 后才读取
- 100ms 后才读取
- 甚至因为程序崩溃，永远没有读取

客户端依然已经收到了 ACK。

## 总结

可以把整个过程理解成下面这张图：

```text
客户端
    │
    │ Send()
    ▼
客户端发送缓冲区
    │
    │ 网络传输
    ▼
服务器 TCP 接收缓冲区
    │
    ├── TCP 自动回复 ACK（表示数据已到达 TCP 层）
    ▼
服务器业务代码（Receive + 处理逻辑）
    │
    ├── 处理成功
    ▼
服务器发送业务响应（例如 AttackOK、BuyResult）
    ▼
客户端收到业务响应
```

因此：

- **TCP ACK**：只能证明**服务器的 TCP 协议栈收到了数据**。
- **业务响应（应用层 ACK）**：才能证明**服务器程序真正读取、处理并完成了这条消息**。

对于游戏开发来说，**任何影响游戏状态的重要操作（登录、购买、战斗、任务等）都应该依赖应用层 ACK，而不是 TCP 的 ACK。**

服务器再次收到。

## 服务器怎么知道这是重复包？

因为 **TCP 每个字节都有序号（Sequence Number）**。

第一次收到：

```text
Seq=100
Length=5

Hello
```

TCP 内部记录：

```text
已经收到：

100~104
```

后来又收到：

```text
Seq=100

Hello
```

TCP 一看：

```text
100~104

已经收过了
```

于是：

```text
丢弃重复数据

再次发送 ACK=105
```

整个过程如下：

```text
第一次：

Hello (100)

↓

服务器 TCP

↓

交给应用层

↓

ACK=105
```

ACK 丢了。

客户端：

```text
超时

↓

重传 Hello(100)
```

服务器：

```text
Seq=100

↓

已经收过

↓

丢弃

↓

ACK=105
```

**不会再次交给你的 `socket.Receive()`。**

---

## 为什么不会交给应用层？

TCP 的职责之一就是：

- 去重（Duplicate Elimination）
- 排序（Ordering）
- 重组（Reassembly）

你的程序看到的永远是：

```text
Hello
World
ABC
```

不会看到：

```text
Hello

Hello

Hello
```

除非你自己发送了三次。

---

## 如果没有这个机制会怎样？

假设 TCP 不去重。

客户端：

```text
购买装备
```

ACK 丢了。

TCP 重传：

```text
购买装备
```

服务器：

```text
扣100金币

再扣100金币

再扣100金币
```

那所有 TCP 应用都会出问题。

所以 TCP 必须保证：

**同一份数据，只交付应用层一次。**

---

## 那应用层为什么还要做幂等？

这里有一个容易混淆的点。

TCP **不会因为 ACK 超时重传，而让应用层收到重复数据。**

但是下面这种情况会：

客户端代码：

```csharp
Send(BuySword);
```

5 秒后：

```text
服务器一直没回业务响应
```

于是你自己的业务代码决定：

```csharp
Send(BuySword);
```

注意！

这是：

**新的 Send。**

不是 TCP 重传。

服务器收到的是：

```text
BuySword

BuySword
```

TCP 会认为：

```text
两个不同的数据包
```

都会交给服务器程序。

所以：

```text
TCP 去重

≠

业务去重
```

---

## 游戏里为什么要有消息 ID？

很多游戏协议都会这样设计：

```text
消息ID：1001

协议：购买

道具：Sword
```

服务器：

```text
已经处理过：

1001
```

如果客户端因为业务超时再次发送：

```text
1001
```

服务器：

```text
直接返回之前的结果

不重复扣钱
```

这叫做**幂等（Idempotency）**。

---

## 总结

可以把两种"重发"区分开：

| 情况 | 谁重发 | 服务器应用层会收到几次？ |
|------|--------|------------------------|
| TCP ACK 超时，TCP 自动重传 | TCP 协议栈 | **1 次**（TCP 自动去重） |
| 你的代码再次调用 `Send()` | 应用层 | **多次**（每次都会收到） |

所以：

> **TCP 的重传不会导致服务器业务代码收到重复消息，因为 TCP 会根据 Sequence Number 自动识别并丢弃重复数据。真正需要业务层做幂等处理的是应用程序主动重发同一业务请求，而不是 TCP 的自动重传。**

这也是为什么在网络面试中经常会问一句话：

> **TCP 保证的是"可靠传输"，而不是"业务不重复执行"。**

这两者是不同层面的保证。

如何同步客户端和服务器时间

### 助手

这是网络游戏中一个非常重要的话题。实际上，**几乎所有联网游戏都会做客户端和服务器时间同步**，因为客户端本地时间既不准确，也可能被用户修改。

常见的同步方法有几种，按精度和复杂度递增介绍。

---

# 方法一：直接获取服务器时间（最简单）

客户端登录后：

```text
Client -------> Login
Client <------- ServerTime = 1718188800
```

客户端保存：

```csharp
serverTime = 1718188800;
localStartTime = Time.realtimeSinceStartup;
```

以后获取服务器时间：

```csharp
long GetServerTime()
{
    return serverTime +
           (long)(Time.realtimeSinceStartup - localStartTime);
}
```

例如：

服务器：

```text
12:00:00
```

客户端收到：

```text
12:00:00
```

十秒后：

```text
12:00:10
```

这种方法实现非常简单。

# Unity 中一般怎么实现？

一般维护：

```csharp
double serverTime;
double localTime;
```

同步：

```csharp
serverTime = serverTimestamp;
localTime = Time.realtimeSinceStartupAsDouble;
```

获取：

```csharp
double Now()
{
    return serverTime +
           (Time.realtimeSinceStartupAsDouble - localTime);
}
```

这里推荐使用：

```csharp
Time.realtimeSinceStartupAsDouble
```

不要：

```csharp
DateTime.Now
```

因为：

- 玩家可以修改系统时间。
- `DateTime.Now` 会受到时区、夏令时等影响。
- `Time.realtimeSinceStartupAsDouble` 是 Unity 提供的单调递增时间，更适合计算时间差。

之后：

- 排行榜刷新
- 世界 Boss 开启

```text

=

LocalMonotonicTime

+

Offset
```

客户端永远不会相信自己的系统时间。

## 推荐的方案（Unity 客户端）

对于 Unity 网络游戏，我推荐下面这种实现：

1. **登录时同步 3~5 次服务器时间**，选择 **RTT 最小**的一次计算时间偏移。
2. **保存 `Offset = ServerTime - Time.realtimeSinceStartupAsDouble`**。
3. 平时获取服务器时间：

```csharp
double ServerNow()
{
    return Time.realtimeSinceStartupAsDouble + offset;
}
```

4. **每 30~60 秒重新同步一次**。
5. 如果新的偏移与当前偏移相差较大（例如超过 100ms），**不要立即跳变**，而是在若干帧内逐步调整 `offset`，避免倒计时、动画和技能 CD 出现突变。

这种方案实现简单、性能开销极低，而且精度通常可以达到几十毫秒，足以满足绝大多数联网游戏的需求。
