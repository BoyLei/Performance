# 一、首先确定场景的整体结构

我不建议一开始就将 256m × 256m 的地图拆成几十个独立 Scene。

对于这种尺寸的 MMO 地图，可以先使用**一个主 Scene + 多个场景物件 Chunk Prefab**。

```text
Map_001.unity
    ├── Terrain
    ├── Physics
    │     ├── TerrainCollider
    │     ├── BuildingColliders
    │     └── RoadColliders
    ├── Lighting
    ├── Water
    ├── Navigation
    └── WorldStreamingManager
          ├── GrassStreaming
          ├── TreeStreaming
          └── BuildingStreaming
```

地形和必要碰撞体先保持常驻，草、树、建筑表现层独立流式加载。

这样设计有一个好处：**即使建筑模型还没有加载完成，角色也不会因为碰撞体缺失而穿过建筑。**

当然，如果地图的碰撞数据非常大，后续也可以单独实现 Physics Streaming。

| 参数 | 示例设置 | 含义 |
|--------|--------|--------|
| Terrain Width | 256 | X 轴长度 |
| Terrain Length | 256 | Z 轴长度 |
| Terrain Height | 50 | 最大地形高度范围 |

| Detail Resolution | 1024 | 草地分布数据分辨率 |

这里重点讲 Heightmap 和 Detail Resolution。

### Heightmap Resolution = 513 是什么意思？

表示地形由 513×513 个高度采样点描述。

对于 256m 长的地形：

\[
采样间距=\frac{256}{513-1}=0.5m
\]

也就是每隔 0.5 米记录一个地形高度。

Heightmap 原理示意。实际渲染网格会根据地形 LOD 动态调整，并非始终绘制全部采样点。

TerrainCollider 也可以使用同一份 TerrainData。

不需要为每个地形格子创建一个独立 Collider。

## m

每个小格代表一个 Patch，绿色区域为相机附近的示意绘制区域。超过 64×64 Patch 时采用简化显示，不代表实际 Unity 剔除结果。

假设使用：

```text
Terrain Size                = 256m
Detail Resolution          = 1024
Detail Resolution Per Patch = 32
```

那么整个 Terrain 被划分为 32×32 个草地 Patch，每一个 Patch 覆盖 8m×8m 的区域。

Unity 会利用这些区域组织草地绘制和剔除。

Patch 设置过大，容易绘制不必要的草；设置过小，则可能增加批次和管理开销。

**但是，这 1024 个 Patch 不会生成 1024 个独立文件。** 草地分布数据仍然存储在 TerrainData 中。

# 四、如果草地需要真正流式加载，应该怎么做？

有两种方案。

## 方案 A：直接拆分 Terrain

将 256m×256m 的 Terrain，拆成 16 个 64m×64m 的 Terrain Tile。

在 Unity Terrain 的 `Create Neighbor Terrains` 工具中可以创建相邻地形。

但注意，该工具不是自动将已有大地形的所有数据均匀切割成小块。已有地图需要使用 Terrain 工具或自定义 Editor 脚本处理。

拆分过程需要重新分配：

- Heightmap。
- Alphamap。
- Detail Layers。
- TreeInstances。
- Terrain Holes。
- 地形邻接关系。

最终产物：

```text
Map_001/
    ├── Terrain_0_0.prefab
    ├── Terrain_0_0.asset
    ├── Terrain_0_1.prefab
    ├── Terrain_0_1.asset
    └── ...
```

每个 Prefab 引用独立的 TerrainData，然后通过 Addressables 加载。

这种方式的缺点是：卸载 Terrain 时，地形表面及其附属草地、树、碰撞体可能会一起消失。

如果你希望地形始终存在，仅草地流式加载，那么方案 B 更适合。

## 方案 B：地形常驻，草地数据独立导出

很多项目会将 Unity Terrain 当作美术编辑工具，然后在构建阶段提取草地数据。

Unity 提供：

```csharp
terrainData.detailPrototypes;
terrainData.GetDetailLayer(...);
terrainData.detailResolution;
terrainData.detailResolutionPerPatch;
```

可以读取美术绘制的草地分布数据。

例如：

```csharp
TerrainData data = terrain.terrainData;

// 读取第 0 种草的分布数据
int[,] density = data.GetDetailLayer(
    0,
    0,
    data.detailWidth,
    data.detailHeight,
    0);
```

然后自定义按照 16m×16m 或 32m×32m 划分空间区域，导出数据。

最终产物可能是：

```text
Grass/
    ├── GrassPrototype.asset
    ├── Grass_0_0.bytes
    ├── Grass_0_1.bytes
    ├── Grass_1_0.bytes
    └── Grass_1_1.bytes
```

每个文件保存密度数据，或者预先生成的草地实例信息：

```csharp
public struct GrassInstance
{
    public Vector3 Position;
    public float Rotation;
    public float Scale;
    public int PrototypeId;
}
```

运行时：

```text
加载 Grass Chunk 数据
        ↓
生成实例矩阵或 GPU Buffer
        ↓
GPU Instancing / Indirect Drawing
        ↓
距离剔除 / 视锥剔除
        ↓
离开范围后释放 Chunk 数据
```

原生 Detail 密度数据并不是最终的草地实例坐标。如果你需要通过自研渲染器尽可能还原原生草的分布，可以进一步研究 `TerrainData.ComputeDetailInstanceTransforms()`。

导出完成后，运行时 Terrain 应去除或禁用原生草地绘制，避免重复渲染；如果目的是节约数据内存，还需要从运行时 TerrainData 中移除不再使用的 Detail 数据。

这种方式比较适合自研 GPU 草系统。

# 五、建筑如何在 Unity 中实现流式加载？

建筑和草不同，因为 Unity 没有内置建筑流式加载管理器。

需要自己制作分块工具。

## 1\. 美术制作完整场景

```text
Map_001_Editor.unity
    ├── Terrain
    ├── House_001
    ├── House_002
    ├── Wall_001
    ├── Stone_001
    ├── Tree_001
    └── ...
```

美术不需要手动关心每栋建筑属于哪一个 Chunk。

## 2\. 编写 Editor 分块工具

假设 Chunk Size = 32m。

那么 256m×256m 的地图可以分成 8×8，共 64 个 Chunk。

计算建筑归属：

```csharp
public static Vector2Int GetChunkId(
    Vector3 position,
    Vector3 mapOrigin,
    float chunkSize)
{
    Vector3 local = position - mapOrigin;

    return new Vector2Int(
        Mathf.FloorToInt(local.x / chunkSize),
        Mathf.FloorToInt(local.z / chunkSize)
    );
}
```

例如一个建筑位于：

```text
Position = (70, 0, 102)
ChunkSize = 32

ChunkX = 2
ChunkZ = 3
```

那么这个建筑就属于 `Chunk_2_3`。

对于跨多个 Chunk 的大型建筑，不能仅依赖中心点判断何时加载。应该记录建筑的 Bounds，提前加载进入关注范围的跨块建筑，并保证只创建一次。

## 3\. 导出 Chunk Prefab

使用 Editor API：

```csharp
PrefabUtility.SaveAsPrefabAsset(
    chunkRoot,
    "Assets/Map/Chunks/Chunk_2_3.prefab"
);
```

最终生成：

```text
Map_001_Runtime.unity

Chunks/
    ├── Building_0_0.prefab
    ├── Building_0_1.prefab
    ├── Building_2_3.prefab
    └── ...
```

注意：运行时 Scene 不能继续引用完整的建筑 GameObject，否则分块就失去意义。

因此最好明确区分编辑场景和运行场景。

## 4\. 设置 Addressables

打开：

`Window > Asset Management > Addressables > Groups`

将 Chunk Prefab 设置成 Addressable。

例如：

```text
Group: Map_001_Chunks
    ├── Building_0_0
    ├── Building_0_1
    ├── Building_2_3
    └── ...
```

Bundle Mode 可以先尝试 `Pack Separately`，让 Chunk Prefab 具有较独立的 Bundle 加载粒度；公共 Mesh、Material、Texture 应另外规划共享依赖，避免重复打包。

需要注意，Chunk 也不是越独立越好，过多的小 Bundle 同样会增加加载和管理成本。

```csharp
public enum ChunkState

    Loaded,
    Unloading
```

# 七、碰撞体和服务器 NavMesh 如何设置？

先在完整的编辑场景中，把建筑的显示和碰撞分开。

```text
House_001
    ├── Visual
    │     ├── MeshRenderer
    │     └── LODGroup
    └── Collision
          ├── BoxCollider
          └── MeshCollider
```

在导出运行时地图时：

- Visual 放入对应 Building Chunk。
- Collision 放入常驻 Scene。
- Collision 不要引用高精度渲染 Mesh，尽可能使用简单 Collider 或低模碰撞 Mesh。

这样建筑资源流式加载时，就不影响角色移动和导航阻挡。

然后通过 Unity 的 AI Navigation 配置：

`Window > Package Manager > AI Navigation`

安装兼容版本后，创建一个 GameObject，添加 `NavMeshSurface`。

image_group{"query":["Unity AI Navigation NavMeshSurface inspector Use Geometry Physics Colliders Collect Objects All Bake"],"aspect_ratio":"16:9","layout":"carousel","num_per_query":1}

示例参数：

| 设置 | 推荐初始值 |
|--------|--------|
| Agent Radius | 0.4m |
| Agent Height | 2m |
| Max Slope | 45° |
| Step Height | 0.3m |
| Collect Objects | All |
| Use Geometry | Physics Colliders |
| Include Layers | 地形、建筑碰撞、道路等 |

Agent 的尺寸参数在对应 Agent Type 中设置。

确保完整地图的导航几何全部加载后，点击 Bake。

然后通过：

```csharp
NavMesh.CalculateTriangulation();
```

可以获得导航表面的顶点、三角形索引和区域类型。

至于最终输出成什么服务器文件，需要与你们服务器现有的导航读取格式保持一致。这个阶段不需要为了客户端 Streaming 而重新设计服务器寻路库。

## 一、分块前后有什么区别？

假设场景中有 6 栋建筑，分布在两个区域。

**分块前**

加载 Scene 时，6 栋建筑全部创建。

**分块后**

建筑成为独立 Prefab 资源，按需加载。

分块之后，每栋建筑依然是独立的 GameObject，MeshRenderer、MeshFilter、Transform、LODGroup 等组件都可以保持不变。

只是给它们增加了一个共同的父节点。

这就是最基础的建筑分块流式加载。

## 三、多个 GameObject 能不能真正合并成一个？

可以，但那是另一项技术，叫做 **Mesh Combine（网格合并）**。

Unity 提供了：

```csharp
Mesh.CombineMeshes();
```

它可以将多个 Mesh 的顶点、索引等几何数据转换到统一坐标空间，合并成一个新的 Mesh。

但是它不会自动合并 GameObject 上的脚本、Collider、Animator 等其他组件。

## 四、两种方案有什么区别？

| 对比 | Chunk Prefab 分组 | Mesh Combine |
|--------|--------|--------|
| GameObject 数量 | 基本不变 | 可以减少 |
| Mesh 数量 | 不变 | 可以减少 |
| Renderer 数量 | 不变 | 可以减少 |
| Draw Call | 不一定减少 | 满足材质等条件时可以减少 |
| 独立视锥剔除 | 支持 | 合并后粒度变粗 |
| 独立 LOD | 保留 | 需要重新设计 |
| 资源流式加载 | 支持 | 需要额外实现 |
| 单独移动建筑 | 可以 | 不方便 |

Mesh Combine 甚至可能导致性能下降。

例如将 30 栋建筑合并为一个 Mesh，只要其中一栋进入相机视野，整个合并 Mesh 就可能参与绘制，失去了逐栋建筑剔除的优势。

## 五、为什么一定要从 Scene 中移出去？

假设你只是把建筑组织成：

```text
Map.unity
    ├── Terrain
    ├── Chunk_0_0
    │     ├── House_A
    │     └── House_B
    └── Chunk_0_1
          ├── House_C
          └── House_D
```

即使你把所有 Chunk 都设置为 `SetActive(false)`，加载 Scene 时，这些 GameObject 仍然会被反序列化创建，其引用的资源通常也需要加载。

只是没有激活和渲染而已。

而将 Chunk 保存为独立 Prefab，并从 Scene 中移除实例及不必要的直接资源引用之后，才可以做到真正的按需加载。

**所以你可以把这两项技术理解为：**

- **Chunk Streaming：决定哪些建筑需要加载到内存。**
- **Mesh Combine：决定已经加载的建筑如何组织渲染。**

我前面讲的是第一种，并不要求你把一个 Chunk 内的所有建筑合并成一个 Mesh。

### 第一步：计算整个建筑的 Bounds

```csharp
public static Bounds CalculateBounds(GameObject building)
{
    var renderers =
        building.GetComponentsInChildren<Renderer>(true);

    if (renderers.Length == 0)
        return new Bounds(building.transform.position,
                          Vector3.zero);

    Bounds bounds = renderers[0].bounds;

    for (int i = 1; i < renderers.Length; i++)
    {
        bounds.Encapsulate(renderers[i].bounds);
    }

    return bounds;
}
```

这样即使一个建筑由几十个 MeshRenderer 组成，也能获得一个完整包围盒。

### 第二步：计算 Bounds 覆盖的 Chunk

由于 Chunk 是固定大小的规则网格，根本不需要遍历所有 Chunk。

直接根据 Bounds 的最小值和最大值计算即可。

```csharp
public static void RegisterBuilding(
    int buildingId,
    Bounds bounds,
    Vector3 origin,
    float chunkSize,
    int countX,
    int countZ,
    List<int>[] chunkBuildings)
{
    Vector3 min = bounds.min - origin;
    Vector3 max = bounds.max - origin;

    int minX = Mathf.Max(0,
        Mathf.FloorToInt(min.x / chunkSize));

    int maxX = Mathf.Min(countX - 1,
        Mathf.FloorToInt(max.x / chunkSize));

    int minZ = Mathf.Max(0,
        Mathf.FloorToInt(min.z / chunkSize));

    int maxZ = Mathf.Min(countZ - 1,
        Mathf.FloorToInt(max.z / chunkSize));

    for (int z = minZ; z <= maxZ; z++)
    {
        for (int x = minX; x <= maxX; x++)
        {
            int chunkId = z * countX + x;

            chunkBuildings[chunkId].Add(buildingId);
        }
    }
}
```

这个过程在编辑器导出阶段执行一次即可。

即使包围盒边界恰好落在 Chunk 分界线上，多注册一个相邻 Chunk 也没有严重问题。这属于保守空间索引，宁可提前加载，也不要漏掉建筑。

## 使用连续数组代替多个 List

之前的数据结构是：

```csharp
List<int>[] chunkBuildings;
```

它适合编辑器构建，但在最终运行时，可以将它压缩成两个连续数组。

```csharp
public struct ChunkIndex
{
    public int Start;
    public int Count;
}

ChunkIndex[] chunkIndices;

int[] buildingIds;
```

这种存储方式类似 CSR（Compressed Sparse Row，压缩稀疏行）。

**ChunkIndex\[\]**

| Chunk ID | Start | Count |
|--------|--------|--------|

**BuildingIds\[\]**

所有 Chunk 的建筑索引都存储在同一个连续 int 数组中。

查询代码：

```csharp
public void CollectBuildings(
    int chunkId,
    HashSet<int> result)
{
    ChunkIndex index = chunkIndices[chunkId];

    int end = index.Start + index.Count;

    for (int i = index.Start; i < end; i++)
    {
        result.Add(buildingIds[i]);
    }
}
```

这种结构具有几个优势：

- 内存连续，CPU Cache 友好。
- 不需要大量 List 对象。
- 查询 Chunk 索引是 O(1)。
- 适合直接进行二进制序列化。
- 后续容易改造成 NativeArray + Job System。

对于建筑数量很多的静态地图，我会优先使用这种数据结构。

# 七、如何避免跨 Chunk 建筑的重复加载及错误卸载？

这是整个设计中最重要的运行时问题之一。

假设：

```text
Chunk 1 → Building A
Chunk 2 → Building A, Building B
```

玩家同时处于 Chunk 1 和 Chunk 2 的加载范围内。

如果你让每个 Chunk 独立管理建筑的创建和销毁，就会面临：

- Building A 被重复创建。
- Chunk 1 卸载时错误销毁 Chunk 2 仍需要的 Building A。
- 异步加载尚未完成，玩家已经离开当前区域。

你可以用引用计数解决，但对于这种静态地图，我更倾向于使用**需求集合（Required Set）**，避免复杂的引用计数管理。

## 每次更新计算当前需要的建筑集合

```csharp
private HashSet<int> requiredBuildings = new();
private HashSet<int> activeBuildings = new();
private List<int> removeBuffer = new();
```

更新过程：

```csharp
public void UpdateStreaming(List<int> requiredChunks)
{
    requiredBuildings.Clear();

    // 1. 收集所有 Chunk 需要的建筑
    foreach (int chunkId in requiredChunks)
    {
        CollectBuildings(chunkId, requiredBuildings);
    }

    // 2. 加载新增建筑
    foreach (int buildingId in requiredBuildings)
    {
        if (activeBuildings.Add(buildingId))
        {
            RequestLoad(buildingId);
        }
    }

    // 3. 收集不再需要的建筑
    removeBuffer.Clear();

    foreach (int buildingId in activeBuildings)
    {
        if (!requiredBuildings.Contains(buildingId))
        {
            if (CanUnload(buildingId))
                removeBuffer.Add(buildingId);
        }
    }

    // 4. 卸载建筑
    foreach (int buildingId in removeBuffer)
    {
        activeBuildings.Remove(buildingId);
        RequestUnload(buildingId);
    }
}
```

这里 `activeBuildings` 表示已经请求加载或仍然保留的建筑，而不仅仅是加载完成的建筑。

`CanUnload()` 需要考虑保留距离和延迟卸载时间。

异步加载完成时，还要再次检查建筑当前是否仍然需要；如果已经不需要，则释放对应资源。正式实现中可以增加请求版本号，避免旧请求完成后覆盖新请求的状态。

## 如果 HashSet 也需要优化呢？

建筑 ID 是连续整数的话，甚至可以不使用 HashSet 做候选建筑去重，而是使用一个 `int[]` 标记数组。

```csharp
int[] visitVersions;
int currentVersion;

List<int> candidates = new();
```

```csharp
public void BeginCollect()
{
    currentVersion++;
    candidates.Clear();
}

public void AddCandidate(int buildingId)
{
    if (visitVersions[buildingId] == currentVersion)
        return;

    visitVersions[buildingId] = currentVersion;

    candidates.Add(buildingId);
}
```

例如：

```text
CurrentVersion = 100

Chunk 1 → Building A, B
Chunk 2 → Building A, C
Chunk 3 → Building A, D

最终候选列表 → A, B, C, D
```

不需要哈希计算，不需要每次清空整个标记数组，也不需要为每个建筑维护 Chunk 引用计数。

只需要注意版本号溢出时统一重置标记数组。

## 3\. Unity Editor 如何自动生成这些 ID？

可以通过 Unity 的 `PrefabUtility.GetCorrespondingObjectFromSource()` 获取场景中 Prefab 实例对应的源资源。

```csharp
        buildingInstance);

```

假设编辑器遍历所有建筑，使用一个 Dictionary：

```csharp

List<PrefabData> prefabs = new();
List<BuildingData> buildings = new();
```

当第一次遇到某种 Prefab 时，为它分配 ID：

```csharp
if (!prefabIdMap.TryGetValue(guid, out int prefabId))
{
    prefabId = prefabs.Count;

    prefabIdMap.Add(guid, prefabId);

    prefabs.Add(new PrefabData
    {
        Id = prefabId,
        Address = address
    });
}
```

其中 `address` 需要从该资源的 Addressables 配置中取得。

```csharp
buildings.Add(new BuildingData

    Position = buildingInstance.transform.position,
    Rotation = buildingInstance.transform.rotation,
    Scale = buildingInstance.transform.lossyScale,
```

# 三、如何在编辑器中构建这两个连续数组？

其实非常简单。

编辑器阶段仍然使用容易操作的：

```csharp
List<int>[] chunkBuildings;
```

等所有建筑注册完成后，再统一转换。

```csharp
public static void BuildChunkIndex(
    List<int>[] chunkBuildings,
    out ChunkIndex[] chunkIndices,
    out int[] buildingIds)
{
    chunkIndices = new ChunkIndex[chunkBuildings.Length];

    int totalCount = 0;

    foreach (var list in chunkBuildings)
    {
        totalCount += list.Count;
    }

    buildingIds = new int[totalCount];

    int offset = 0;

    for (int i = 0; i < chunkBuildings.Length; i++)
    {
        List<int> list = chunkBuildings[i];

        chunkIndices[i] = new ChunkIndex
        {
            Start = offset,
            Count = list.Count
        };

        list.CopyTo(buildingIds, offset);

        offset += list.Count;
    }
}
```

整个转换只在地图导出阶段执行一次。

运行时不需要重新构建，也不需要排序建筑 ID。

# 四、为什么要这么设计？有必要吗？

假设有 256 个 Chunk，50,000 条建筑空间索引记录。

| 对比 | List\<int>\[\] | int\[\]\[\] | 连续数组 |
|--------|--------|--------|--------|
| List 对象数量 | 256 | 0 | 0 |
| 内部数据数组 | 最多 256 个 | 256 个 | 1 个 |
| 容量冗余 | 可能存在 | 无 | 无 |
| 动态增删 | 方便 | 不方便 | 不方便 |
| 内存连续性 | 较差 | 分段连续 | 整体连续 |
| 二进制序列化 | 相对复杂 | 简单 | 简单 |
| 查询复杂度 | O(K) | O(K) | O(K) |

连续数组的索引数据占用：

```text
ChunkIndex[]：
256 × 8 = 2,048 Bytes

BuildingIds[]：
50,000 × 4 = 200,000 Bytes

合计：
202,048 Bytes ≈ 197.3 KiB
```

不包含数组对象头及建筑本身的数据。

不过，对于你们这种 128m 或 256m 的地图，使用 `int[][]` 其实也完全可以。连续数组并没有改变算法的时间复杂度，主要优化的是内存布局、对象数量和缓存局部性。

| 2 | Buildings/House\_Garden |

运行时不需要关心 Override，直接根据 PrefabId 加载即可。

### 优点

- 不需要自研 Override 序列化系统。
- 原始 Prefab 修改后，未被覆盖的属性可以继续继承更新。
- 可以复用 Mesh、Texture、Material 等资源。
- 支持新增组件、子节点及属性覆盖。

### 缺点

如果美术摆放了 1000 栋建筑，每栋建筑都有一点不同，就可能产生大量 Prefab Variant。

另外，Prefab Variant 不能直接删除继承自基础 Prefab 的 GameObject，通常需要将其禁用。如果必须改变基础层级结构，可以考虑独立 Prefab。

# 四、方案二：将微调记录为实例参数

假设美术只是修改了建筑的颜色、整体缩放或者某些装饰物的显示状态。

那么没有必要生成新的 Prefab。

可以扩展之前的 `BuildingData`：

```csharp
[Serializable]
public struct BuildingData
{
    public int PrefabId;

    public Vector3 Position;
    public Quaternion Rotation;
    public Vector3 Scale;

    public Bounds Bounds;

    // 自定义实例参数
    public Color RoofColor;
    public bool ShowFlowerpot;
    public int MaterialId;
}
```

运行时加载基础 Prefab 后，再应用这些参数。

```csharp
GameObject instance = await LoadBuilding(data.PrefabId);

instance.transform.SetPositionAndRotation(
    data.Position,
    data.Rotation
);

instance.transform.localScale = data.Scale;

var view = instance.GetComponent<BuildingView>();

view.SetRoofColor(data.RoofColor);
view.SetFlowerpotVisible(data.ShowFlowerpot);
view.SetMaterial(data.MaterialId);
```

这样即使 1000 栋建筑的颜色都不同，也可以只使用一个基础 Prefab。

但这种方式需要提前约定哪些属性允许被参数化，不能自动支持美术任意修改组件。

# 五、方案三：编辑器自动检测 Override 并生成 Prefab

我认为这个方案比较适合你们的地图导出流程。

美术不需要手动创建大量 Variant，仍然可以直接在完整场景中修改建筑。

地图导出工具负责检测这些修改。

Unity 提供了相关 Editor API：

```csharp
PrefabUtility.GetPropertyModifications(instance);

PrefabUtility.GetObjectOverrides(instance);

PrefabUtility.GetAddedGameObjects(instance);

PrefabUtility.GetAddedComponents(instance);

PrefabUtility.GetRemovedComponents(instance);
```

也可以先进行整体检测：

```csharp
bool hasOverrides =
    PrefabUtility.HasPrefabInstanceAnyOverrides(
        instance,
        false
    );
```

第二个参数 `false` 表示不将默认 Override 纳入检测。但仍然需要根据自己的导出规则过滤已经保存的 Transform 等属性。

# 六、如何避免生成大量重复的 Variant？

假设有以下建筑：

| 建筑实例 | 原始 Prefab | 美术修改 |
|--------|--------|--------|
| Building 0 | House | 蓝色屋顶 |
| Building 1 | House | 蓝色屋顶 |
| Building 2 | House | 红色屋顶 |
| Building 3 | House | 蓝色屋顶 |
| Building 4 | House | 无修改 |

没有必要生成四个 Variant，只需要生成两个。

可以在编辑器导出阶段，对原始 Prefab GUID 和规范化后的 Override 内容计算 Hash。

```text
PrefabKey = Hash(
    PrefabGUID + OverrideData
)
```

然后通过 Dictionary 进行去重：

```csharp
Dictionary<string, int> prefabKeyToId;
```

最终结果：

| BuildingId | PrefabId | 实际资源 |
|--------|--------|--------|
| 0 | 1 | House\_Blue |
| 1 | 1 | House\_Blue |
| 2 | 2 | House\_Red |
| 3 | 1 | House\_Blue |
| 4 | 0 | House |

需要注意，计算 Hash 时应该排除建筑整体位置、旋转、缩放等已经单独保存的属性，否则每个建筑都会得到不同的 Hash。

如果需要支持新增节点、组件以及对象引用，还需要对这些结构差异进行稳定的序列化，不能简单地只对 `PropertyModification.value` 计算 Hash。

# 七、生成新的 Prefab 会不会增加资源内存？

需要区分 Prefab 和它引用的资源。

例如：

```text
House.prefab
House_Blue.prefab
House_Red.prefab
        │
        ├── House.mesh
        ├── Wall.texture
        └── Roof.texture
```

即使存在三个 Prefab，也不代表 Mesh 和 Texture 一定会存在三份。

只要它们引用的是相同的资源，并且 AssetBundle 依赖打包正确，就可以共享底层资源。

不过大量 Variant 仍然会增加 Prefab 序列化数据、资源管理以及加载请求的开销。

# 八、我建议你们采用的规则

| 修改类型 | 导出策略 |
|--------|--------|
| 整体 Transform | 保存到 BuildingData |
| 高频且可预定义的属性修改 | 保存为实例参数 |
| 低频的复杂属性修改 | 自动生成 Prefab Variant |
| 建筑结构发生较大变化 | 生成独立 Prefab 或 Variant |
| 完全相同的修改 | 复用已生成的资源 |

对于第一版地图流式加载系统，我甚至不建议实现完整的 Override Hash 去重系统。

可以先实现：

**原始 Prefab + Transform 数据 + 自动检测 Override + 必要时生成 Variant。**

等实际统计发现 Variant 数量过多，再考虑参数化和自动去重。

这样既不会限制美术的场景编辑自由度，也不需要在运行时实现一套复杂的 Prefab Override 还原系统。
