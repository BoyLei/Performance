## 托管与原生所有权

C# 对象位于托管内存，Unity 对象还关联原生对象；纹理和网格可能存在 CPU 与 GPU 副本。托管引用释放、Destroy、Addressables Release 和显存回收不是同一时刻。

**验证与验收：** 在空场景、加载后、销毁后、释放后各抓快照，比较引用链和原生对象。

## GC分配与卡顿

装箱、闭包、字符串拼接、临时集合和部分枚举路径可能产生分配。减少每帧分配能降低回收压力，但零 GC 不保证零卡顿。增量 GC 将部分工作分散，仍有成本与适用条件。

**验证与验收：** 用 GC.Alloc 调用栈定位热点，复测 P95/P99 帧耗时而非只看平均 FPS。

## 对象池与峰值

池减少反复创建销毁，却会保留对象和资源引用。池容量应有上限、回收策略和重置协议；超量预热会增加启动耗时和常驻内存。

**验证与验收：** 往返场景十次后检查池、事件监听和资源引用是否回到稳定水平。

## 字符串与缓冲区

StringBuilder 对多次构建字符串可降低中间字符串数量，但 ToString 仍创建结果字符串；简单短字符串未必受益。历史中 Streambuilder 按上下文对应 StringBuilder，原字词保留在索引。

**验证与验收：** 比较热路径分配，检查日志与 UI 格式化频率。

## 堆、栈与 Unity GC 的边界（Q130–Q135）

内存中的托管堆不是最小堆数据结构。class 实例通常在托管堆上，但局部引用可在寄存器、栈或状态机字段中；struct 可内嵌于堆上的数组/对象，也可被装箱。不要从类型名推导实际存储位置或分配成本。

Unity 2022.3 的 Boehm GC（含增量模式）不采用现代桌面 .NET 的分代压缩模型。旧 StringBuilder 回答里的“减少 Gen0 搬移”不能直接用于解释 Unity：可成立的是减少中间字符串分配与复制，进而降低回收压力。缓冲区扩容、最终 ToString、日志及格式化仍可能分配；实现也可能采用分块缓冲而非每次复制整块。

foreach 遍历具体 List/Dictionary 与经接口枚举的行为不同；调用 GetComponent、RemoveAt 或事件 Invoke 也不能仅凭名称判定必然分配。Profiler 的 GC.Alloc 是分配证据，GC 回收暂停是另一项测量。
