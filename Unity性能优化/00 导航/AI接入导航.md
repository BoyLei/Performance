## 先确认工作版本

在仓库根目录执行下面的只读检查，记录实际 HEAD、分支与工作区。远端有新提交时先核对差异；不要覆盖用户尚未提交的内容，也不要假定上一次 PR 仍未合并。

```bash
git status --short
git branch --show-current
git log -5 --oneline
git remote -v
git merge-base --is-ancestor 490076d HEAD
```

`490076d` 是初始交接提交，**不是后续所有任务的文件保护基准**。从已审阅的当前工作版本记录本轮 `BASE_REF`，后续用它检查本轮是否改动无关文件。保护配置与原件的比较应同时覆盖已提交和未提交差异；新建文件另看 `git status`。

## 两种接管范围

### 单模块完善

1. 读当前用户目标与 `AGENTS.md`，明确模块、问题、允许改动范围和预期交付。
2. 读本页、[[文件核验报告]] 最新章节及 [[知识关联核验]] 中相关关系；旧报告中的目录和统计只是当时快照。
3. **全文读取**目标模块、它的专项、相关前置模块；根据 [[历史问题索引]] 的 Q 编号读取对应原文，而不是只读历史标题、整理摘要或旧助手结论。
4. 读 [[知识点逐项核验]] 的对应条目、[[技术核验来源]] 和 [[参考资料与版本边界]]；技术争议查官方文档或固定版本源码。
5. 读对应 Canvas、[[知识体系脑图]]、[[学习任务脑图]] 与 [[未讨论与待核实路线]] 的相关部分，再开始编辑。

只读了相关原文就只能报告相关范围，不能写成“重读了全部历史”。不需要为了一个模块顺手重写其他模块。

### 全库历史覆盖或遗漏核对

从仓库的 `云端交接/00 云端继续前先读.md` 开始，按其中顺序读取缺口说明、当前聊天快照及全部 36 份现存历史原文；大文件分段读完。随后对照 [[历史原问覆盖与缺口]]、[[逐份原文核对记录]] 和 [[历史检索与整理说明]]。

交接包是只读的历史快照，其中旧目录、文档数与运行验证状态可能已过时；当前布局查 `工具/知识结构.json` 与最新核验报告，**不要为了让旧路径成立而回退现有目录**。36 份片段、136 条用户消息不等于完整历史，也不等于 136 个独立技术问题。缺图、缺附件、未交付 Demo 和未实测项仍是缺口。

`AGENTS.md` 是接入路由，本页是工作说明，`知识结构.json` 是覆盖清单，技术正文和版本来源才是技术内容依据。三者不能互相替代。

## 当前检查器的边界

> [!important] 为后续模块完善保留的说明
> `verify_structure.py` 包含针对 `d8883d3` 重组前正文的逐字保全检查，并固定了 10 模块、7 专项、99 技术小节、13 Canvas 等当前库存。**这是重组时的保护断言，不是禁止今后完善内容。**

以后经用户授权修改正文或新增小节时，原保全断言/固定计数可能预期失败。接手 agent 应区分格式错误与授权内容变更：先用本轮 `BASE_REF` 对照实际 diff，证明无关模块、来源与配置仍受保护；再把检查器/清单更新为适合本轮的受审基线和明确范围（新目录的文件路径也需一并处理）。不要只改一个总数、删除断言、把 baseline 指向自己的未审提交或覆盖原文来“刷绿”。本次接入文档任务不更改这些技术正文冻结规则。

`verify_vault.py --base-ref` 只控制文件改动范围的保护比较，**不会**替换 `知识结构.json` 的正文保全基线。两个基准不是同一件事。

在当前仓库根目录运行：

```bash
# 把 BASE_REF 替换成任务开始前记录的真实提交，例如本次文档任务的 745b3a8。
python Unity性能优化/工具/verify_vault.py --base-ref BASE_REF
python Unity性能优化/工具/verify_structure.py
python Unity性能优化/工具/verify_history_coverage.py
python Unity性能优化/工具/test_markdown_structure.py
python Unity性能优化/工具/verify_knowledge_math.py
git diff --check
```

Python 检查依赖 PyYAML。修改 Mermaid 时另按 `工具/verify_mermaid.mjs` 文件头安装指定版本的外部依赖并执行；机器上的临时依赖路径不是仓库文件，不保证跨会话存在。结构测试和算式检查通过不等于技术结论、Unity 性能或插件展示已验证。

## 多 agent 接力与交付

- 采用“一个模块、一个明确目标、一个分支/PR”的工作粒度；先检查当前分支与未合并 PR，避免重复处理同一任务。
- 不覆盖其他 agent 或用户的工作区。并行时由各自分支处理模块正文；共享清单、首页、关系表和图谱由合并者统一核对，冲突按内容语义解决。
- 每次交接在 [[文件核验报告]] 顶部补本轮范围、基准、修改、来源、验证结果及未解决项；不重新生成整套知识库，不把旧截图当新证据。
- PR 描述对应最终内容；是否提交、推送或建 PR 按本次用户授权与当前环境执行，不沿用旧历史里的行动承诺。
- 对外报告具体通过了什么、没有测什么；不编造整体正确率，不自动勾选学习任务。
