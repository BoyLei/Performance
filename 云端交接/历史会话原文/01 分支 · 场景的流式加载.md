- 合并重复知识点，保留不同问题的分析角度。
- 保留你提出的实际项目场景和技术疑问。
- 修正历史回答中不准确或者容易产生误解的结论。

**1\. 核心概念**

渲染合批的目的主要是降低渲染提交成本，不同合批技术优化的阶段不同。

**3\. 核心原理**

SRP Batcher 优化材质常量数据的管理与绘制准备过程，并不直接将多个 Draw Call 合并为一个。

GPU Instancing 通过共享 Mesh 数据及使用实例数据，在一次实例化绘制中绘制多个物体。

**4\. 历史问题**

- 为什么 SRP Batcher 和 GPU Instancing 提交的顶点数相同？
- 为什么 MPB 会影响 SRP Batcher？
- 大量堆叠石头应该采用哪种合批方式？
- 场景流式加载是否影响合批？

**5\. 方案对比**

|--------|--------|
| SRP Batcher | CPU 渲染提交 |
| GPU Instancing | Draw Call 数量 |

# 四、如何处理知识点之间的关联

我会采用三种方式，它们分别解决不同的问题。

## 4.1 层级脑图：知识的归属关系

用于 Mind map editor 插件展开、折叠及勾选知识点。

底层采用标准 Markdown 层级结构，尽量不依赖插件私有的数据格式。

## 4.2 双向链接：跨模块知识关联

使用 Obsidian 原生的 `[[文档名称]]` 语法。

例如，在 SRP Batcher 文档中引用：

```markdown
SRP Batcher 的实现涉及：

- [[GPU 内存与带宽#Constant Buffer]]
- [[材质与 MPB]]
- [[Shader Pass 与 Variant]]
- [[GPU 渲染管线]]
```

这样点击对应链接，就可以跳转到其他模块的具体知识点。

Obsidian 的关系图谱也可以根据这些链接展示整个知识库的关联。

## 4.3 Mermaid：原理、因果和执行关系

普通脑图只能表示父子层级，但很多技术知识之间存在因果关系、依赖关系和执行顺序。

这部分使用 Obsidian 原生支持的 Mermaid 图表。
